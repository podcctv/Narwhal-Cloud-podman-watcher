# Runman Rust v2 compatibility

Updated for Watcher v1.8.29 and Runman Rust v2.0.4 inventory schema 1. This is a source-level compatibility matrix; it does not claim that a live Runman host was exercised.

## Supported

| Capability | Status and boundaries |
| --- | --- |
| Inventory and identity | Instance UUID, replacement generation, running state, image, IPs, CPU/memory limits and usage come from Runman's root-only Unix socket. Controls that can mutate a guest or network are bound to the current generation. |
| TCP connections and traffic | Fresh TCP state counts are checked against the instance generation. Cumulative byte counters feed Watcher's traffic ledger and rate calculations; a restart or new generation starts with a fresh baseline. |
| Resource and filesystem metrics | Fresh Runman history samples expose CPU, disk usage/read/write rates and IOPS, network rates, TCP/UDP flow counts and remote-IP count. Root and `/data` filesystem capacity use the generation-checked init PID and guest `df` fallback. |
| Writable overlay layer | Runman reports allocated blocks for unique entries and logical lengths of regular files below the mounted overlay `upperdir/up`, separately from sparse `disk.img` host allocation and guest filesystem usage. Sampling is bounded to 50,000 entries and is available only while the same instance generation is running and the upper mount remains active. Symlinks are never followed; hard links count once; an incomplete or over-limit walk is unavailable. Logical regular-file bytes exclude directory metadata, symlink targets, xattrs and whiteout archive overhead. The Watcher drawer labels both values and their sources. |
| Process and security scans | The Watcher uses bounded guest exec for generic read-only process, listener, SOCKS and protocol inventory, and merges those results with Runman metrics. The endpoint binds UUID plus generation, limits each command to 90 seconds and caps combined output at 64 KiB. Manual and alert-triggered deep snapshots are also generation-bound and remain read-only. Specialized protocol guards and service actions have separate runtime gates listed below. |
| Connection evidence timeline and replay | Read-only history views accept Runman UUID targets and group samples by the latest verified instance generation, so restarts do not blend old and new instance evidence. Replay and operator feedback do not change enforcement policy. |
| Shell card and MOTD | Watcher installs its interactive-shell card through generation-bound guest exec. It updates `/etc/motd` through checked procfs when possible and falls back to an atomic guest-exec update/create after rejecting symlinks and non-regular files. Explicit per-user security notices can target Runman when the alert and latest report prove the same UUID generation; retries and delivery verification keep that generation. Shell delivery is reported separately from whether a user saw it. |
| SSH pre-authentication banner | For Runman only, Watcher can install a managed `sshd_config.d` drop-in and banner file through generation-bound guest exec when the active config includes that directory before `Match`. It preserves any operator `Banner`, validates with `sshd -t` and `sshd -T`, reloads the active service and checks readback. Missing OpenSSH, unsupported Include layout, operator directives or unavailable reload are reported without claiming activation. |
| Host firewall and temporary TCP limit | The Runman bridge participates in host RFW interface discovery/readback. Temporary TCP limits continue to require a live UUID, fresh connection evidence and matching generation. |
| Public endpoint monitoring | Runman reports are included in the GFW endpoint discovery scan. A public listener is eligible only when a public guest IP is directly reported or an explicit host-DNAT target matches the guest IP and a live listener; the public host IP/interface and unique container ownership must also be verified. Upstream NAT is never guessed. |
| Network quarantine | The Watcher can quarantine a Runman instance by lowering its Runman-owned host veth, recording desired state first, and reading the link state back. Release is generation-bound and reversible; Runman reapplies the recorded state after restart/heal. |
| Automatic abuse detection and quarantine | Runman is included in the bounded abuse scan. It requires two fresh corroborating samples, validates the current UUID generation and guest process incarnation, then quarantines only the instance-owned host veth; the alert API accepts only a canonical VM UUID, UUID v4 generation and the `default` project. |
| Admission protection | Runman is sampled through its current UUID generation and init PID. Watcher reads TCP state in that PID's network namespace, confirms the reported IPs on guest interfaces, proves each external address is behind the instance-owned host veth/bridge, and then applies/readbacks the host nftables/NFQUEUE rule. Shared namespaces, stale PID/generation, missing addresses, and non-veth networking remain unprotected/unknown; no address-only fallback is used. |
| Bounded disk cleanup | Runman is eligible for the existing scan/cleanup workflow when the host policy enables it. The default policy remains disabled. Before opening `/proc/<init-pid>/root`, the Agent checks the exact UUID generation and PID from Runman's root-only API, private PID namespace, process start ticks, filesystem root and mount ID. Cleanup remains limited to known historical log/archive paths, no-follow traversal, mount boundaries, retention, byte/file/time budgets, and per-file revalidation. |
| PasarGuard Node cleanup | The exact Go ELF build module can be detected in Runman processes. Cleanup uses the existing bounded guest exec and current UUID generation, rechecks the process/network incarnation before and after execution, and only disables/stops the identified service using supported manager adapters. It does not stop the Runman guest or delete user data. |
| Per-instance bandwidth limits | Manual and automatic limits use `tc` in the instance's network namespace. The target is the current generation. Automatic limits start only when Watcher proves the dedicated network namespace, selected uplink path and fresh traffic sample; rates are policers, so packets above the rate are dropped. |
| UDP socket and process attribution | Rust inventory reports fresh guest network-namespace UDP socket counts when both IPv4/IPv6 TCP and UDP tables parse completely. Watcher attributes visible TCP and connected UDP table entries by socket inode; it reports UDP file-descriptor references for unconnected sockets. Shared inherited descriptors can appear for each owning process, so these are process references rather than unique network sockets. Missing procfs permissions or incomplete snapshots remain unavailable. |
| CPU offender attribution | A bounded one-second guest `/proc` CPU-time delta identifies the top process for Runman CPU pressure alerts. The generic container report also uses guest `ps` when available; unavailable process snapshots remain unknown. |
| Dynamic CPU, memory and I/O guards | Runman guards can lower and restore `cpu.max`, `memory.high` and per-device `io.max` on the verified `system.slice/runman-<uuid>.service/ct` cgroup. Every access rechecks the live PID start ticks, exact VM UUID and cgroup boundary. The guard remains unavailable when cgroup v2 controllers/files are absent or readback no longer matches the saved state. |
| Sustained resource overload restart | Server tracks fresh Runman generations and queues a restart only after CPU or memory is at least 90% for 3600 seconds, at least five valid samples, and no sample gap over 900 seconds (defaults). Only Client Agent v1.8.28 or newer is eligible. Agent re-reads inventory and the current metric, checks the expected node/generation, takes a host lock, refuses an existing systemd job, and restarts only `runman-<uuid>.service`; it requires the unit's exact cgroup and confirms an active unit with a changed MainPID. Existing `ct/io.max` entries are snapshotted and restored with readback. The action does not delete the guest or its disk image. |
| Speed-test and VMess/Trojan guards | Explicitly selected Runman instances can receive the existing bounded speed-test service policy and protocol-specific network-namespace port rules. Rules require complete process/config/listener evidence and post-apply readback. Runman is selectable per saved policy; the no-policy automatic default firewall policy includes Runman alongside Incus/Podman. Blocked, partial, release-pending and unverified outcomes now produce the same protocol alert receipts as Incus/Podman. |
| Reviewed SOCKS process stop | An administrator can explicitly stop only the reviewed SOCKS process PIDs after the server confirms a fresh matching Runman report generation. The Agent checks the live instance generation, review token and each PID start tick before signaling, then verifies the process is gone. It does not stop the guest or establish a persistent weak-password block. |
| Panel and XMRig cleanup | Runman supports the existing allowlisted panel/XMRig cleanup actions. The alert, action queue and Agent carry the VM UUID generation, exact PID plus `/proc` start tick, and per-file device/inode/size/mtime/ctime/mode fingerprint. The Agent rechecks all evidence before mutation and rechecks each process/file immediately before service stop, signaling or unlinking. It only targets approved panel config paths, exact XMRig config/binary paths, and regular service files named by an allowlisted process pattern or observed in that process's cgroup. Service stop supports systemd, OpenRC and SysVinit (`update-rc.d` or `chkconfig` plus the exact executable init script). Symlinks, recursive service scans and incomplete evidence are skipped. Legacy alerts without these fields remain notice-only. |
| Action affordances | The dashboard and alert history now expose panel/XMRig remediation for Runman only when the alert contains a valid default-project UUID v4 generation and a valid process-start or file-fingerprint target. SOCKS weak-auth persistent enforcement remains unavailable for Runman; an administrator-reviewed exact-PID stop is supported. |
| Sustained-overload automatic stop | After the server observes the required continuous fresh samples, the Agent sends the expected UUID generation and threshold to Runman's root-only control API. Runman holds the instance lifecycle lock, checks that exact managed generation is still running and still above the selected TCP-active or all-socket threshold, then records the stopped desired state and halts it. A replacement, recovered load, stale evidence or older Runman API fails closed. The action stops the guest; it never deletes it. |

## Remaining boundaries

| Capability | Current boundary |
| --- | --- |
| Exact Podman metric parity | Runman exposes regular-file logical bytes and filesystem allocated blocks. Podman's storage library defines `DiffSize` as an estimate of the layer-diff tar stream ([upstream interface](https://github.com/containers/storage/blob/main/layers.go)), which includes serialization semantics Runman does not reproduce; exact `SizeRw` parity is therefore not claimed. Compare only values with their source labels. |
| Cleanup coverage | Cleanup remains limited to local allowlists, exact process generations and regular-file fingerprints. Arbitrary recursive deletion, s6/runit/custom service managers, symlink targets, changed generations and incomplete evidence remain manual-review cases. |
| Persistent SOCKS weak-auth policy | Runman supports an explicit administrator-reviewed stop of the exact SOCKS process after current-generation and process-evidence checks. A persistent policy that repeatedly stops SOCKS after a service restart is intentionally not enabled for Runman, because the existing saved policy is name-scoped and does not yet carry a generation-bound review contract. |

## Runtime requirements

- Runman must expose `/run/narwhal-agent/connlimit.sock` with root-only permissions, and Watcher must run with access to that socket. Older Runman builds without `/v1/exec`, `/v1/network-quarantine` and `/v1/stop-overload` can still provide supported read-only inventory, but scans, shell/SSH banner installation, reviewed SOCKS stop, Admission, PasarGuard/disk cleanup, panel/XMRig cleanup, automatic overload stop, quarantine and Runman bandwidth controls require the updated API.
- `CONTAINER_RUNTIMES` must be `auto` or include `runman`; a setting containing only `podman` excludes Runman inventory.
- Guest execution requires a running, managed instance and matching generation. Commands that exceed the timeout or output bound fail without being reported as successful.
- SSH Banner additionally requires OpenSSH server files and service-management support inside the guest. A configured banner file does not prove that every SSH client displayed it.
- Resource guards require cgroup v2 with the corresponding controller delegated to the exact Runman `ct` cgroup. Runman does not create missing controllers or invent a finite baseline.
- Automatic resource restart requires the Watcher Agent to run on the Runman host with root/systemd access and the exact `runman-<uuid>.service` unit. The action is serialized with Watcher's restart lock and systemd jobs, but the current Runman API does not expose a lifecycle-locked restart endpoint; a concurrent Runman API lifecycle change can still race the short gap between the final inventory check and systemd request. Hosts without systemd, matching cgroup identity, current metrics, or an available restart lock fail closed.
- Filesystem/MOTD procfs access additionally requires a readable process root and stable init PID start ticks. When procfs cannot safely update MOTD, guest exec performs bounded regular-file/symlink checks before an atomic write.
- Network shaping and quarantine require an existing Runman veth and a verified, dedicated network namespace. Shared/unreadable namespaces, stale identities, missing interfaces or uncertain routes cause the operation to fail closed.
- No live SSH display or production node was verified as part of this source change.
