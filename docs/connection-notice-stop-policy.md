# 连续连接超限：先通知后停机（1.7.40）

管理员策略：当前连接数严格大于 2000，连续有效采样覆盖至少 300 秒，先向该用户发停机前提醒，再关闭容器，不删除数据。

统计口径保持 TCP 各状态 + UDP socket 总数，不解释为人数或 HTTP 请求数。1000 的严重告警线不变，停机门槛单独为 2000。
五分钟窗口至少需要两个新鲜有效样本；同一容器/网络代次、中间没有回落到 2000 或以下，最大采样间隔 360 秒。
缺失、过期、乱序、重启、数据口径不完整均不延长连续时长。策略变化会重新建立窗口，旧的六小时告警时长不能直接用作新停机证据。

达到门槛后异步排队定向用户通知。只有买家通知 API 确认受理，才原子登记带通知凭证的停机动作。
停机前提醒拥有高于普通通知冷却的优先级，但不与同一机器正在发送的请求并发，不重复发送同一窗口事件。
缺少精确收件映射、通知关闭、发送失败或结果不确定时，不下发停止指令，界面策略字段明确提示等待通知或管理员核查。
API 已受理不是用户已读；系统无法保证 Telegram 用户已读。系统不会因超时盲目重发，也不会整机广播。
SSH 登录提醒独立写入；容器停止后无法登录，不作为“用户已收 Telegram”的证明。

API 回执后若窗口已经回落、重启或过期，不排队停止。节点真正执行前再次验证当前连接仍大于 2000、容器代次未变、证据未过期及通知凭证存在。
Docker notice-only 仍不自动停止。停止回执独立记录在连接保护告警，不把排队或 API 受理文案当成关闭成功。

生产升级必须同时设置 CONNECTION_STOP_THRESHOLD=2000、CONNECTION_STOP_DURATION_SECONDS=300、CONNECTION_STOP_MAX_GAP_SECONDS=360；已有环境文件值不会仅因代码默认值改变而被覆盖。
